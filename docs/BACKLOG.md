# Backlog

Work queue for `rhood-rs` — a Rust workspace exposing the Robinhood brokerage API as a
library (`rhood-core`), a CLI (`rhood-cli`), and an MCP server (`rhood-mcp`).

Domain vocabulary lives in [`CONTEXT.md`](../CONTEXT.md); architectural decisions live in
[`docs/adr/`](./adr/). Both were created by the 2026-08-09 grill — before it, several rows
below existed only because a deliberate-looking choice had no recorded reasoning to check
against.

**Decisions that constrain this backlog.** Rows must be read against these; a row that
predates one and contradicts it is wrong, not the ADR:

- [ADR-0001](./adr/0001-strict-2026-07-28-only.md) — serve MCP `2026-07-28` only. Single
  stateless path, no legacy session routing, per-request protocol metadata enforced.
- [ADR-0002](./adr/0002-mrtr-elicitation-for-trade-confirmation.md) — Confirmation happens
  via MRTR elicitation with sealed `requestState`, not a server-side staged-order map.
- [ADR-0003](./adr/0003-core-owns-instrument-identity-enrichment.md) - `rhood-core` alone owns
  network-backed Instrument Identity Enrichment; CLI and MCP are presentation adapters.
- [ADR-0004](./adr/0004-upstream-responses-are-untrusted-input.md) — an upstream response is
  untrusted input: correlate by an explicit key never by position (single-item requests
  included), never derive an authority-bearing request from response content without
  validating its host against the configured base URLs, and never rely on the peer to
  terminate a loop.

## How items get worked

The gate is `just verify` (`justfile:5-9`), which mirrors CI's
`.github/workflows/pull-request-validation.yml`:

```sh
cargo fmt --all --check
cargo check --locked --workspace --all-targets --all-features
cargo clippy --all-targets --all-features -- -D warnings
cargo nextest run --all-targets --all-features
```

A row is done when `just verify` is green and the change carries a test that would have
failed before it. Since BL-1 landed, all three crates declare `[lints] workspace = true`, so
the 43-lint workspace policy is genuinely enforced and a green `just verify` means what the
config claims.

`just audit` is green on `main` and runs on every PR — see BL-21 and the cleared `## Holds`
entry.

### Scoping a work order's file list

Learned the expensive way (BL-32, after three lost rounds on BL-24). A work order's file list
must be derived from what _breaks_, not from where the changed code lives:

- **Deleting or renaming a symbol?** `rg` for it first and take the file list from the hits.
  BL-24's three STOPs were the runtime construction site, then the tests naming the deleted
  tool, then the generated artefact — all findable in one grep, run only after the second stop.
- **Changing cargo features?** Add `Cargo.lock`. `just verify` runs `cargo check --locked`, so
  a stale lock fails the gate outright.
- **Every "do not touch X" must say why.** BL-24's first STOP was a stale exclusion copied from
  a previous batch whose owning order had already merged. A constraint without a reason cannot
  be re-evaluated, so it rots silently.
- **Documentation lives outside `src/`.** BL-33 exists because a grep scoped to
  `crates/*/src` missed two READMEs describing the deleted tool. **The repository's root
  `README.md` is the doc no crate-scoped fence ever owns** — BL-60 is the third instance of
  this class, so put it in the file list of any order that changes a public interface.
  **Standing rule, adopted with BL-60's close on 2026-08-13:** root `README.md` goes in the file
  list of every order that changes a public interface, without needing to be argued for again.

### This file is the only durable record

**Do not write a `HANDOFF.md`, a session summary, or any other "what to do next" document.**
One existed through 2026-08-12 and was deleted at the operator's direction, because it
duplicated this file and the two could only drift. Everything a next session needs already has
a home here: what to work on next is the **Ranked queue**, what happened is **Tending**, what
was checked and cleared is the **dispositions** blocks, and why a placement was made is the row
or the Inbox preamble. Anything that does not fit one of those is session state, not durable
state, and dies with the session — say it in the final message instead.

Two operational notes that would otherwise have been lost with that file:

- **`wt merge` refuses when `main` is dirty in a file the fence also touched.** It happened on
  BL-58. The safe resolution is to back the file up, `git stash push -- <that one path>`, merge,
  then `git stash pop`; disjoint hunks auto-merge. Never resolve it by discarding or committing
  the operator's uncommitted work.
- **The environment can carry incomplete `GIT_CONFIG_*` variables.** If Git reports a missing
  config key, prefix the command with
  `env -u GIT_CONFIG_COUNT -u GIT_CONFIG_VALUE_0 -u GIT_CONFIG_VALUE_1`.

### Delegated review is not reliable on its own

On 2026-08-12, **three** delegated agents in one session — a verdict reviewer and both axes of a
`code-review` — finished their work and then went idle without delivering it. All three had real
findings; none surfaced until the lead explicitly asked for the report, and one needed two
requests. **Treat a silent agent as unfinished, never as clean.** A review that produced no
findings and a review that never reported are indistinguishable from the outside, and the
default assumption must be the second. Chase every delegated review to an explicit report or do
it yourself; never let an absent verdict read as a pass.

### Accounting for a plan's required proof

Learned on BL-58 (2026-08-12), and cheap to apply. That order shipped green while **three**
tests its own `## Required proof` section named were never built — the summary-coverage
contract test, the deterministic clock seam and its 60s/600s assertions, and three of four CLI
proofs — and nothing upstream noticed, because **a green gate cannot distinguish a missing test
from a passing one**. Two rules follow:

- **A work order must account for every `Required proof` line explicitly, present or absent.**
  "Built" or "deliberately skipped, because …" — never silence. A verdict should check that
  ledger before it checks anything else.
- **A named gate command must be re-run after any module rename, and its output read, not just
  its exit code.** BL-66 exists because `cargo test -p rhood-mcp tools::order` kept exiting zero
  after the proof it was written to select moved to `tools::confirmation`. A gate pointing at
  nothing still passes.

Related: when a symbol moves between layers, diff its *behaviour*, not just its call sites.
BL-63 exists because validation correctly relocated from adapter to core and quietly changed
its limit on the way, taking its only tests with it.

## Ranking criterion

**ADOPTED 2026-08-09 — in practice, never explicitly ratified.** The operator banded the
whole inbox against it without amending it, which is acceptance by use rather than a
stated endorsement; say so plainly if you later disagree with it. Drafted by the bootstrap
run from what the repo evidently cares about (a panic-averse lint policy, a two-step order
confirmation flow, a `SECURITY.md`, and a loud never-in-production warning on the
`test-helpers` feature):

> _Authority over real money first — anything that lets an unintended party place, alter,
> or approve a trade outranks everything. Then credential confidentiality. Then correctness
> of the data a model reasons over. Then ergonomics, structure, and hygiene._

Two placements were the operator's, against the draft's grain, and are worth preserving as
precedent: **BL-1** was moved out of `P0` (a dead lint gate does not itself move money,
whatever it costs the definition of done), and **BL-8** was held at the foot of `P1` rather
than raised for being a spec `MUST`.
